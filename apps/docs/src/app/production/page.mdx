# Production storage, locking, encryption

The vault runs on a deliberately tiny persistence contract. Production is two composed lines; everything below explains what those two lines buy you.

```ts
import { encryptedVaultStore, vaultTokenSource, apsOAuth } from 'aec-auth/vault'
import { upstashVaultStore } from 'aec-auth/vault/upstash'

const store = encryptedVaultStore(upstashVaultStore(), { key: process.env.VAULT_KEY! })
```

## The VaultStore contract

`get`/`set`/`delete`, compare-and-set, plus an ownership-aware renewable lock. Implement it over Redis or another store with the required atomic primitives:

```ts
export interface VaultStore {
  get(key: string): Promise<string | null>
  set(key: string, value: string, opts?: { ttlMs?: number }): Promise<void>
  delete(key: string): Promise<void>
  /** Atomic set-if-not-exists. Resolves an opaque lease when this caller
   *  now holds the lock, null when someone else does. */
  acquireLock(key: string, ttlMs: number): Promise<string | null>
  /** Compare-and-extend only while lease still owns the lock. */
  renewLock(key: string, lease: string, ttlMs: number): Promise<boolean>
  /** Release only if `lease` still owns it — compare-and-delete,
   *  never an unconditional delete. */
  releaseLock(key: string, lease: string): Promise<void>
  /** Atomically replace expected with value, or report that it changed. */
  compareAndSet(key: string, expected: string | null, value: string | null): Promise<boolean>
}
```

### Why locks are leases

`acquireLock` returns an opaque lease. The vault renews that lease throughout the refresh-and-persist critical section; every renewal and release compares the opaque owner first. If ownership is lost, the caller stops before publishing a token. Grant rotation/deletion additionally uses compare-and-set as a fencing check, so a stale process cannot overwrite or recreate changed grant state.

In Redis terms: acquire is `SET key lease NX PX ttl`; renew, release, and grant compare-and-set are Lua scripts. Both shipped stores implement exactly this, and `test/vault-stores.test.ts` is the conformance suite a new store must pass.

## Encryption at rest

`encryptedVaultStore` wraps any store with AES-256-GCM over WebCrypto, so it runs everywhere the core does. Grants (refresh tokens) and cached access tokens are stored as `enc.v1:` + base64 ciphertext; lock leases pass through untouched (random values, not secrets).

```bash
openssl rand -base64 32   # -> VAULT_KEY
```

- **`VAULT_KEY` is 32 bytes, base64 or hex.** Treat it like a database credential.
- **Losing it orphans every stored grant.** There is no recovery — every user re-consents. Back it up like you back up the database it protects.
- **A wrong key fails loudly.** Decryption errors surface as errors; the store never falls back to plaintext, and it refuses to read unencrypted values left over from a store previously used without encryption.
- **Ciphertext binds to its store key.** The store key is AES-GCM `additionalData`, so copying user A's encrypted grant onto user B's key fails decryption instead of letting B refresh with A's grant.

Without this wrapper, refresh tokens sit in your store as readable JSON. Use it — or storage-layer encryption — in production.

## The Upstash store

`upstashVaultStore()` is the reference production store: REST-based, so it runs on Node, edge, and workers alike. `@upstash/redis` is an optional peer — install it alongside:

```bash
pnpm add @upstash/redis
```

Configuration, in order of preference:

```ts
// 1. From env: UPSTASH_REDIS_REST_URL + UPSTASH_REDIS_REST_TOKEN
const store = upstashVaultStore()

// 2. Explicit url/token
const store = upstashVaultStore({ url, token })

// 3. Reuse an existing client — created with automaticDeserialization: false
const store = upstashVaultStore({ redis })
```

The `automaticDeserialization: false` requirement is not optional: vault values are opaque strings (possibly ciphertext), and the SDK's automatic JSON deserialization would mangle them. The store creates its own clients that way; only a client you pass in yourself can get it wrong.

## Full production composition

```ts
// lib/aps.ts
import { apsOAuth, encryptedVaultStore, vaultTokenSource } from 'aec-auth/vault'
import { upstashVaultStore } from 'aec-auth/vault/upstash'

export const store = encryptedVaultStore(upstashVaultStore(), {
  key: process.env.VAULT_KEY!,
})

export const aps = apsOAuth({
  clientId: process.env.APS_CLIENT_ID!,
  clientSecret: process.env.APS_CLIENT_SECRET!,
})

export const tokens = vaultTokenSource({ store, providers: { aps } })
```

With env:

```bash
APS_CLIENT_ID=...
APS_CLIENT_SECRET=...
UPSTASH_REDIS_REST_URL=...
UPSTASH_REDIS_REST_TOKEN=...
VAULT_KEY=...   # openssl rand -base64 32
```

## Memory store: dev only

`memoryVaultStore()` is for development and tests. Two reasons it must not reach production:

- **No persistence.** Grants die with the process; on serverless, that is every cold start — each one a user re-consent.
- **No cross-process lock.** Its lock only exists inside one process. Two serverless instances would refresh the same grant concurrently — precisely the race that bricks single-use APS grants.

The in-process single-flight still works with it, which is why it is fine for `next dev` and unit tests.
